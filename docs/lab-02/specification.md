# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing MVP: a Requester can create an IT support ticket with
attachments, find it again in My Tickets (search/filter/sort/page), open its read-only Ticket Detail,
and manage attachments on it — all scoped to a single selected Requester identity, simulated for now
via a Development Requester selector rather than real login.

## 2. Stakeholder Request Interpretation

The IT department needs a professional, responsive ticket-submission experience before real
authentication exists. Since Lab 3 introduces login, Lab 2 needs a temporary stand-in ("who am I
testing as") so ownership rules can be built and proven now. The interface and data model must be
built as if real users existed, so Lab 3 can swap the temporary selector for real auth without
reshaping Tickets, Attachments, or ownership checks.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism, not authentication)
- Create Ticket (fields, validation, attachment upload, Ticket Number generation)
- My Tickets (search, filter, sort, pagination, ownership-scoped)
- Requester Ticket Detail (read-only ticket header + attachment list)
- Attachment lifecycle: add, download (active only), soft-remove with reason
- Ownership enforcement (a Requester can never read/act on another Requester's Ticket or Attachment)
- Zen Green UI theme and reusable component conventions

### Excluded (explicitly out of scope for Lab 2)
- Authentication, sessions, passwords, tokens, real authorization
- IT Staff dashboard, ticket ownership/assignment, IT Priority, status changes
- Public Comments, Internal Notes, Actions Taken
- Any ticket status beyond the initial `New`
- Administrator functions (user/category/related-system management UI)

## 4. Functional Requirements

- **FR-01** The system provides a Development Requester Selection screen listing only active
  Requesters, loaded from PostgreSQL.
- **FR-02** Selecting a Requester stores that Requester's id as the current testing context
  (client-side) and routes to My Tickets.
- **FR-03** The application shell displays the current Requester's name and a "Change Requester"
  action that returns to the selection screen.
- **FR-04** A Requester can create a Ticket by submitting Summary, Description, Category, Related
  System, Requested Priority, and 0–5 Attachments.
- **FR-05** On successful creation, the backend generates a unique, sequential Ticket Number and
  returns it to the UI, which displays it as the confirmation of success.
- **FR-06** A Requester can retrieve a paginated list of only their own Tickets, with search,
  category/priority/status filters, and column sorting.
- **FR-07** A Requester can open the Ticket Detail screen for a Ticket they own, showing the header
  fields read-only and the attachment list.
- **FR-08** A Requester can add a new Attachment to an existing owned Ticket, subject to the fixed
  attachment rules (type, size, count).
- **FR-09** A Requester can download an active (not removed) Attachment they own.
- **FR-10** A Requester can soft-remove an Attachment they own by providing a removal reason; the
  Attachment's metadata remains visible but it can no longer be downloaded or previewed.
- **FR-11** Any request for a Ticket or Attachment not owned by the current Requester context fails
  safely without revealing whether the resource exists.
- **FR-12** Switching the Development Requester reloads all Requester-scoped data (My Tickets,
  Ticket Detail) for the newly selected identity.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend and must be unique. Format:
  `TKT-{YYYY}-{6-digit sequence}` (e.g. `TKT-2026-000042`), sequence resets per calendar year.
- **BR-02** A new Ticket begins with Current Status `NEW` and no Ticket Owner.
- **BR-03** Lab 2 uses a Development Requester selector instead of login. The selected identity is
  for testing only, is not authentication, and must be removed/replaced in Lab 3.
- **BR-04** Ticket Date, Ticket Number, Current Status, Ticket Owner, and Resolution Summary are
  system-generated/read-only and are never accepted from client input on create.
- **BR-05** Requester, Category, and Related System must reference existing active records; an
  inactive or unknown id is rejected as a validation error.
- **BR-06** Ticket Summary is required, trimmed, and must be 5–150 characters after trimming.
- **BR-07** Ticket Description is required, trimmed, and must be 10–2000 characters after trimming.
- **BR-08** Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH`.
- **BR-09** The Development Requester selector loads only Requesters with `isActive = true`; an
  inactive Requester never appears in the dropdown, and any API call presenting an inactive or
  unknown requesterId is rejected as an ownership/validation failure (400).
- **BR-10** A Ticket belongs to exactly one Requester (the one selected at creation time); ownership
  never changes in Lab 2.
- **BR-11** The My Tickets list only ever returns Tickets whose `requesterId` matches the current
  Requester context — enforced server-side, not just hidden in the UI.
- **BR-12** My Tickets supports search over Ticket Number and Summary (case-insensitive, partial
  match), filtering by Category, Requested Priority, and Current Status, and sorting by Created Date,
  Requested Priority, or Current Status (default: Created Date, newest first).
- **BR-13** Pagination uses 1-based page numbers; default page size is 10, maximum permitted page
  size is 50; invalid page/pageSize values fall back to the defaults rather than erroring.
- **BR-14** If ticket creation fails validation, no Ticket is persisted, no attachment is stored, and
  all submitted field values (except files) are preserved in the form for correction.
- **BR-15** If a Ticket is created successfully but one or more attachment uploads fail, the Ticket
  is still saved; the failed files are reported to the Requester, who may retry adding them from
  Ticket Detail. (Compensation, not all-or-nothing: a Ticket must never be lost because of an
  attachment failure.)
- **BR-16** Attachment allowed types are JPG/JPEG, PNG, WEBP, and PDF; maximum size is 5 MB per file;
  a Ticket may have at most 5 **active** (non-removed) Attachments at a time.
- **BR-17** Attachment files are stored under a generated, non-guessable filename (UUID + original
  extension); the original filename is preserved only as metadata, never as the storage path.
- **BR-18** Removing an Attachment is a soft removal: it sets `removedAt`, `removedReason`, and
  keeps the row. A removed Attachment's metadata (name, size, uploaded date, removed date, reason)
  remains visible in Ticket Detail but its file can no longer be downloaded or previewed.
- **BR-19** Only the owning Requester (the current Development Requester context matching the
  Ticket's requesterId) may add or remove Attachments on a Ticket.
- **BR-20** Removing an Attachment requires the Requester to provide a non-empty removal reason
  (trimmed, 3–200 characters).
- **BR-21** My Tickets shows an **empty state** ("You haven't created any tickets yet" + Create
  Ticket action) when the Requester owns zero Tickets, distinct from a **no-results state** ("No
  tickets match your filters" + Clear Filters action) when filters/search exclude all of an
  otherwise non-empty list.
- **BR-22** Opening Ticket Detail for a Ticket Number that doesn't exist, or exists but is not owned
  by the current Requester context, returns the same safe "Ticket not found" result in both cases —
  the API and UI never distinguish "doesn't exist" from "not yours" to avoid leaking existence.
- **BR-23** Attempting to use My Tickets, Create Ticket, or Ticket Detail before any Development
  Requester has been selected redirects to the Development Requester Selection screen.
- **BR-24** In Lab 3, `requesterId` will come from an authenticated session instead of client-sent
  state; the API layer already treats `requesterId` as the sole ownership key so no schema change is
  expected, only the source of that id changes.

## 6. UI Specification Summary

Full detail lives in `docs/lab-02/ui-spec.md`. Summary:
- **App shell:** TokTickIT identity (left), My Tickets / Create Ticket nav, current Requester name +
  Change Requester (right), active-page indication, responsive hamburger nav on mobile.
- **Development Requester Selection:** title, explanatory text ("not a login screen"), dropdown of
  active Requesters, Continue button, loading/empty/error states, keyboard accessible.
- **Create Ticket:** system-generated fields (Ticket Number, Ticket Date) shown as read-only
  placeholders until saved; classification fields (Category, Related System, Requested Priority)
  grouped; Summary/Description given full width; Attachments below; Submit (primary, busy state) +
  Cancel (secondary) at the bottom; inline field-level validation messages.
- **My Tickets:** search box, filter row (Category/Priority/Status), sortable columns, paginated
  table on desktop, stacked cards on mobile; Create Ticket button; loading/empty/no-results/error
  states.
- **Ticket Detail:** read-only header fields grouped like Create Ticket; Attachments section listing
  active and removed attachments distinctly, with Add/Download/Remove actions and a removal-reason
  dialog.
- All screens use the Zen Green tokens (§7 of the labsheet / `ui-spec.md`) for color, spacing, field
  states, and badges, and follow the responsive breakpoints in `ui-spec.md`.

## 7. Data Changes

New/extended Prisma models (full field list in `ui-spec.md`/Prisma schema, key points here):

- **RequesterUser** — id, name, email (unique), isActive, createdAt. Seed: ≥4 active, ≥1 inactive.
- **RelatedSystem** — id, name (unique), isActive, createdAt. Seed: ≥6 realistic systems.
- **Category** — unchanged model from Lab 1, reused as-is.
- **Ticket** — id, ticketNumber (unique), requesterId (FK → RequesterUser), categoryId (FK →
  Category), relatedSystemId (FK → RelatedSystem), summary, description, requestedPriority (enum),
  currentStatus (enum, default `NEW`), createdAt, updatedAt.
- **Attachment** — id, ticketId (FK → Ticket), originalFilename, storedFilename (unique), mimeType,
  sizeBytes, uploadedAt, removedAt (nullable), removedReason (nullable).

Indexes: unique on `Ticket.ticketNumber`, `RequesterUser.email`, `RelatedSystem.name`,
`Attachment.storedFilename`; index on `Ticket.requesterId` (every My Tickets query filters by it);
index on `Ticket.createdAt` (default sort); index on `Attachment.ticketId`.

Enums: `Priority { LOW MEDIUM HIGH }`, `TicketStatus { NEW }` (single value now, deliberately an enum
so Lab 3+ can extend it without a data migration).

## 8. API Contract

Full contract in `docs/lab-02/api-spec.md`. Endpoints:

| Method & Path | Purpose |
|---|---|
| GET /api/requesters | List active Development Requesters |
| GET /api/categories | List categories (reused from Lab 1) |
| GET /api/related-systems | List active Related Systems |
| POST /api/tickets | Create a Ticket (+ optional attachments) for the current Requester |
| GET /api/tickets | Paginated, searched/filtered/sorted list of the current Requester's Tickets |
| GET /api/tickets/:ticketNumber | One owned Ticket with its attachments |
| POST /api/tickets/:ticketNumber/attachments | Add an Attachment to an owned Ticket |
| GET /api/attachments/:id | Attachment metadata |
| GET /api/attachments/:id/download | Download an active Attachment |
| DELETE /api/attachments/:id | Soft-remove an Attachment (reason required) |

The current Requester context is sent as an `X-Requester-Id` request header on every Requester-scoped
call (a stand-in for the session that Lab 3's auth will provide).

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when the Requester submits Create Ticket, then one Ticket is
  saved and the generated Ticket Number is shown in a success state.
- **AC-02** Given no Development Requester is selected, when the user opens My Tickets, Create
  Ticket, or a Ticket Detail URL directly, then the Requester Selection screen is shown instead.
- **AC-03** Given Requester B is selected, when a Ticket belonging to Requester A is requested (list,
  detail, or attachment), then no data about that Ticket is returned.
- **AC-04** Given the Summary field is empty, when the Requester submits Create Ticket, then a
  field-level validation message is shown and no API request is made.
- **AC-05** Given the Description field is empty, when the Requester submits Create Ticket, then a
  field-level validation message is shown and no API request is made.
- **AC-06** Given a 6th attachment is selected for a Ticket that already has 5 active attachments,
  when the Requester attempts to add it, then the addition is rejected with a clear message and the
  existing 5 remain untouched.
- **AC-07** Given a file larger than 5 MB or of an unsupported type, when the Requester selects it as
  an attachment, then it is rejected client-side with a clear message before any upload is attempted.
- **AC-08** Given the backend is unreachable, when the Requester submits Create Ticket, then a safe
  error state is shown and all previously entered field values remain in the form.
- **AC-09** Given a Requester has zero Tickets, when they open My Tickets, then the empty state (not
  the no-results state) is shown.
- **AC-10** Given a Requester has Tickets but the applied filters match none of them, when they view
  My Tickets, then the no-results state (with a Clear Filters action) is shown.
- **AC-11** Given a Requester types part of a Ticket Number or Summary into search, when the list
  reloads, then only matching Tickets owned by that Requester are shown.
- **AC-12** Given more Tickets exist than one page can show, when the Requester pages forward/back,
  then the correct subsequent/previous page of their own Tickets is shown.
- **AC-13** Given a Requester opens Ticket Detail for one of their own Tickets, when the page loads,
  then all header fields are shown read-only and match the stored Ticket.
- **AC-14** Given a Requester adds a valid Attachment from Ticket Detail, when the upload succeeds,
  then the Attachment appears in the active list immediately without a full page reload.
- **AC-15** Given a Requester removes an active Attachment with a reason, when the removal succeeds,
  then the Attachment is shown as removed (metadata visible, no download link) and its removal reason
  is displayed.
- **AC-16** Given a removed Attachment, when a Requester attempts to download it (including by
  guessing/replaying its download URL), then the download is rejected.
- **AC-17** Given the Requester selection dropdown is loading, when the Development Requester
  Selection screen first renders, then a loading state is shown before the list appears.
- **AC-18** Given no active Development Requesters exist, when the selection screen loads, then an
  empty state is shown instead of an empty/broken dropdown.
- **AC-19** Given the viewport is narrower than 768px, when any Lab 2 screen is viewed, then no
  horizontal page scrolling occurs and all controls remain reachable and legible.
- **AC-20** Given a Requester switches to a different Development Requester via Change Requester,
  when the switch completes, then My Tickets reloads and shows only the newly selected Requester's
  Tickets.

## 11. Assumptions and Decisions

- **Requester context transport:** the selected Requester id is sent as an `X-Requester-Id` header
  rather than a query/body param, so every Requester-scoped route can enforce ownership in one place
  (middleware) instead of re-checking per handler. This mirrors how a real auth middleware will slot
  in during Lab 3 (replacing the header read with a session/JWT read).
- **Ticket Number format:** `TKT-{year}-{6-digit sequence}` was chosen to match the example UI shown
  in the labsheet (`TKT-2025-001234`) while keeping the sequence readably short; uniqueness is
  enforced by a DB unique constraint plus a transactional increment, not by re-checking existence.
- **Attachment storage:** local disk under `server/uploads/` (gitignored), served through an
  authenticated-by-ownership download route rather than static file serving, so removed/foreign
  attachments can never be fetched by guessing a URL.
- **404 vs 403 for ownership failures:** Lab 2 always returns 404 for both "doesn't exist" and "not
  yours" (BR-22/AC-03) to avoid confirming a Ticket Number's existence to a non-owner.
- **Pagination defaults:** page size 10 / max 50, chosen to match the illustrative My Tickets screen
  in the labsheet ("Showing 1 to 8 of 42 tickets" implies a small default page).
